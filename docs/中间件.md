上一版**提到了中间件相关能力，但没有把 Middleware 作为独立架构层完整设计出来**。对于你这个要做成通用 FastAPI Admin Framework 的项目，建议补上，而且不要把所有东西都做成 Middleware。

建议增加：

```text
server/app/core/
├── middleware/
│   ├── request_id.py
│   ├── access_log.py
│   ├── cors.py
│   ├── trusted_host.py
│   ├── security_headers.py
│   ├── timing.py
│   └── context.py
│
├── security/
├── rate_limit/
└── exceptions/
```

其中我认为 **第一版真正必要** 的是：

| Middleware       | 必要性   | 作用                            |
| ---------------- | ----- | ----------------------------- |
| Request ID       | 必须    | 每个请求生成/透传唯一 ID                |
| Request Context  | 必须    | 保存 request_id、当前用户等请求上下文      |
| Access Log       | 必须    | 方法、URL、状态码、耗时等                |
| CORS             | 必须    | Admin 前后端分离访问控制               |
| Trusted Host     | 生产必须  | 防止非法 Host Header              |
| Security Headers | 生产必须  | 基础 HTTP 安全响应头                 |
| Timing           | 推荐    | 记录接口耗时                        |
| GZip/Brotli      | 可选    | API 大响应压缩                     |
| Rate Limit       | 必须有能力 | 登录/API 等限流，但不一定自己造 Middleware |
| Maintenance Mode | 后续    | 系统维护时阻止普通请求                   |

不过有几个功能**不要错误地塞进 Middleware**。

认证不建议做成一个巨大的：

```text
AuthMiddleware
```

FastAPI 更适合：

```python
Depends(get_current_user)
Depends(require_permission("users.update"))
```

也就是：

```text
Request
   │
   ├─ Middleware
   │   ├─ Request ID
   │   ├─ Context
   │   ├─ CORS
   │   ├─ Security
   │   └─ Logging
   │
   ▼
FastAPI Router
   │
   ├─ Authentication Dependency
   └─ Permission Dependency
          │
          ▼
       Service
```

这样 `/health`、`/docs`、登录接口、公开 API、Admin API 可以分别决定是否认证，不会被一个全局 Auth Middleware 搞得非常僵硬。

同理，**RBAC 不能靠 Middleware 完成**。Middleware 不知道 `users.update`、`orders.export` 这种业务语义。应该：

```python
@router.patch("/{id}")
async def update_user(
    ...,
    user = Depends(
        require_permission("users.update")
    )
):
    ...
```

然后 Resource Engine 可以进一步自动生成这些 Permission Dependencies。

### Rate Limit 建议设计成独立 Core 能力

不要只有：

```text
RateLimitMiddleware
```

而应该：

```text
core/rate_limit/
├── backend.py
├── redis.py
├── limiter.py
├── policy.py
└── dependency.py
```

支持：

```text
Global
IP
User
Route
Resource
Action
```

例如：

```text
普通 API
100 req/min

Login
5 req/min/IP

Password Reset
3 req/10min

Export
5 req/min/user
```

以后复杂业务也可以：

```text
AI API
20 req/min/user
```

所以它应该是 **Rate Limit Engine + Dependency/Middleware Adapter**，而不是写死一个全局限流中间件。

### Request Context 非常值得加

建议统一：

```python
request_context.request_id
request_context.user_id
request_context.ip
request_context.user_agent
```

然后 Service、Audit、Logging、Event 都可以获得上下文。

例如：

```text
HTTP Request
     ↓
RequestContextMiddleware
     ↓
request_id = abc123
user_id = 1001
     ↓
Service
     ↓
Event
     ↓
Audit
```

最后日志：

```json
{
  "request_id": "abc123",
  "user_id": 1001,
  "method": "PATCH",
  "path": "/api/v1/users/10",
  "status": 200,
  "duration_ms": 18
}
```

出了问题可以通过一个 `request_id` 串起整条链路。

### Middleware 顺序也应该写进开发约束

中间件不是注册了就结束，顺序很重要。建议定义明确的 Pipeline，例如概念上：

```text
Request
   ↓
Trusted Host
   ↓
CORS
   ↓
Request ID
   ↓
Request Context
   ↓
Access Logging / Timing
   ↓
Security / Rate-limit policy
   ↓
FastAPI Router
   ↓
Authentication Dependency
   ↓
Permission Dependency
   ↓
Service
   ↓
Response
   ↓
Security Headers
   ↓
Access Log
```

实际实现时还要结合 FastAPI/Starlette 的 middleware 包装顺序验证，**不能根据上面图示直接假定注册顺序等于执行顺序**，必须有集成测试。

### 还有一个很重要的约束：Middleware 不能访问业务 Module

继续遵循你前面的架构：

```text
core/middleware/
```

只能依赖：

```text
Core
Infrastructure
Config
Logging
```

禁止：

```python
from modules.users.service import ...
from modules.trading.service import ...
```

也就是说：

> Middleware 是基础设施，不是业务逻辑容器。

否则以后非常容易出现一个 `AuthMiddleware.py` 1000 行，里面同时查用户、角色、菜单、权限、订阅、会员状态。

### 建议把上一版开发文档第 62 节升级

不要只写：

```text
API Security
├── Authentication
├── Authorization
├── CORS
├── Trusted Hosts
├── Validation
└── Security Headers
```

正式增加一个 **Middleware & Request Pipeline** 模块：

```text
Core Middleware
│
├── Request ID               MUST
├── Request Context          MUST
├── Access Logging           MUST
├── CORS                     MUST
├── Trusted Host             PROD MUST
├── Security Headers         PROD MUST
├── Request Timing           RECOMMENDED
├── Compression              OPTIONAL
├── Rate Limit Adapter       REQUIRED CAPABILITY
└── Maintenance Mode         OPTIONAL
```

同时明确：

```text
不属于 Middleware：

Authentication     → FastAPI Dependency
Authorization/RBAC → FastAPI Dependency
Validation         → Pydantic
Business Logic     → Service
Database           → Repository
Audit              → Event/Audit Service
Exception Mapping  → Exception Handler
```

这最后一条也很重要：**全局异常处理优先使用 FastAPI Exception Handler，不要做成 Exception Middleware。**

所以现在这份架构还需要补一章 Middleware。我会把 **Request ID + Context + Logging + CORS + Trusted Host + Security Headers** 定为 Admin Framework Core 的基础能力；Rate Limit 做成独立 Engine；认证和 RBAC 坚持 Dependency 模式。这样边界会比很多 FastAPI Admin 项目清楚得多。
