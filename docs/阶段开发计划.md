# FastAPI Vue Admin 阶段开发计划

**状态：** 当前执行计划  
**原则：** 以阶段门禁推进，不以代码量、页面数量或 API 数量作为完成标准。

## P0：Repository Foundation

完成目录、FastAPI、Vue3、TypeScript、pnpm、SQLAlchemy、Alembic、Redis、Docker、Scalar、OpenAPI 和质量工具基线。

门禁：后端、前端可启动；`/api/health`、`/openapi.json`、`/docs/scalar` 可访问；迁移可往返；Redis 缺失不阻断基础 Web。

## P1：Component Foundation

### P1A：shadcn-vue

完成官方组件初始化和源码预置，锁定版本，验证 TypeScript、Lint、Build、Dark Mode。

### P1B：AI Elements Vue

接入 `components/ai-elements/`，完成依赖、类型、构建和 Smoke Test；不接入真实 AI Provider。

### P1C：Admin Semantic Components

实现 `AdminPage`、`AdminPageHeader`、`AdminToolbar`、`AdminSearch`、`AdminFilter`、`AdminPagination`、`AdminConfirm`、`AdminLoading`、`AdminError` 和 `PermissionGuard`。

### P1D：Admin Shell

实现 Sidebar、Header、Breadcrumb、动态导航、路由状态、折叠、移动端和用户菜单逻辑。

门禁：不依赖具体业务即可展示完整 Admin Shell；不引入第二套 UI Framework；官方视觉基线未被修改。

## P2：Backend Core 与 ORM

完成数据库 Session、生命周期、Users/Roles ORM、Pydantic Schema、Repository、Service、Router、Alembic 和双数据库验证。

目录必须采用：

```text
server/app/modules/users/{module,model,schema,repository,service,router,resource,permissions,events}.py
server/app/modules/roles/{module,model,schema,repository,service,router,resource,permissions,events}.py
```

门禁：Router 不访问数据库；普通业务无 Raw SQL；重复记录返回 409；数据库未配置返回明确 503；PostgreSQL/MySQL 使用同一套业务代码通过测试。

### P2 当前实现状态（2026-09-19）

- 已完成 FastAPI 应用、真实 `/api/v1/health`、可选数据库/Redis 探测和稳定错误码。
- 已完成 Users/Roles SQLAlchemy 2.x Async ORM、Repository、Service、Router、Alembic 初始迁移。
- 已完成 OpenAPI → TypeScript SDK 生成，并由 Dashboard 健康 Adapter 调用。
- 已通过 SQLite 隔离测试和 Alembic 往返测试；PostgreSQL/MySQL 双库集成需在配置实际账号后执行。
- 本项目后端开发端口为 `8012`，`8011` 已被其他本地服务占用；前端 Vite 代理已同步指向 `8012`。

## P3：Authentication 与 RBAC

完成登录、登出、当前用户、JWT/OAuth2 基础认证、User/Role/Permission、Route Guard、Action Guard、Menu Guard、Data Scope 和 Audit 基础能力。

门禁：未登录和越权测试通过；所有权限由后端强制执行；审计包含操作者和 Request ID；Secret 不进入日志和审计。

### P3 当前实现状态（2026-09-19）

- 已完成 Users/Roles 管理页面的真实列表和创建表单，创建动作使用生成的 TypeScript SDK。
- 已完成前端 Route Guard、Menu Guard 和 `users.view` / `users.create` / `roles.view` / `roles.create` 权限过滤。
- Roles API 已返回排序后的权限代码，Roles 页面使用 Badge 展示角色实际权限。
- 已补齐 `users.delete` / `roles.delete`：后端 DELETE API 强制校验权限，前端仅向有权限的用户显示删除操作，并在删除后刷新列表。
- 已补齐 `roles.update`：支持通过 `PUT /api/v1/roles/{id}/permissions` 更新角色权限集合，前端提供权限代码编辑入口并校验权限存在性。
- 已补齐 `users.update`：支持通过 `PUT /api/v1/users/{id}/roles` 维护用户角色绑定，Users 页面展示角色并提供受权限控制的编辑入口。
- 已建立 Audit 基础：新增 `audit_logs` 表和 0003 迁移，写入角色/用户变更的操作者、动作、资源、资源 ID 与 Request ID；响应统一返回 `X-Request-ID`。
- 已提供 `audit.view` 权限保护的 `/api/v1/audit-logs` 查询 API 和 Audit 管理页面，支持查看最近审计记录。
- 已增加受 `roles.view` 保护的 `/api/v1/permissions` 权限目录 API，按权限代码稳定排序；前端新增权限目录页面，使用真实 API 展示注册权限。
- 已增加角色 `data_scope`（`all` / `self`）字段、0010 Alembic 迁移和受 `roles.update` 保护的更新 API；Roles 页面可编辑并展示数据范围，Users 查询及角色更新、单条删除、批量删除在 `self` 范围下均执行当前用户约束，权限代码继续作为独立 Action Guard。
- 后端权限依赖和 API 契约测试通过；组织/团队级 Data Scope、字段级权限和更细粒度的用户-角色绑定仍属于 P3 后续工作。

## P3.3：Middleware Foundation

建立生产级请求管线，但不复制 FastAPI/Starlette 已经提供的路由、请求、响应、验证和异常处理能力。

### P3.3 设计基线

- 设计文档：[P3.3-中间件基础设施设计.md](./P3.3-中间件基础设施设计.md)
- Core Middleware 只依赖配置、上下文、日志和基础设施，禁止依赖业务 Module。
- Authentication、RBAC、Data Scope 继续使用 FastAPI Dependency、Policy、Service 和 Repository，不实现巨型 Auth Middleware。
- Middleware 顺序必须通过集成测试验证，不能只依赖注册顺序的推断。

### P3.3 实施范围

1. Request ID。
2. Request Context。
3. JSON Access Log。
4. Request Timing。
5. CORS 配置。
6. Trusted Host。
7. Security Headers。
8. 通用错误响应与 Request ID 关联。
9. Middleware 集成测试和配置测试。

### P3.3 不纳入范围

- Rate Limit Engine，进入 P3.4。
- OpenTelemetry Exporter，进入 P3.7。
- Server-side Session、gRPC、邮件、文件存储和 AI SDK。
- 自定义 Router、Controller、Request、Response、Validation 或 ORM。

### P3.3 门禁

- 正常响应和错误响应都有可追踪 Request ID。
- 日志不泄露 Authorization、密码、JWT、数据库 URL 和 Redis URL。
- 非法 Host 被拒绝，CORS 来源按环境配置生效。
- 安全响应头覆盖正常和异常响应。
- 现有 Auth/RBAC/Data Scope/Audit/Task 测试无回归。
- 后端测试、前端测试、类型检查、生产构建和 SDK 一致性检查通过。

### P3.3 当前进度

- 已完成 Request ID、Request Context、JSON Access Log、Timing、CORS、Trusted Host 和 Security Headers 的基础实现。
- 已接入真实 FastAPI 应用，并通过 63 个后端测试、前端测试、类型检查、生产构建和 SDK 一致性校验。
- 保留 1 个既有 SQLAlchemy 异步资源释放警告，作为后续测试基础设施清理项，不影响本阶段功能门禁。

## P4：Task Engine 与基础设施

采用 `arq + Redis` 执行、数据库任务记录与 outbox。完成入队、幂等、重试、退避、取消、进度、Worker、故障恢复、Redis 降级和任务权限。

门禁：业务事务与任务记录同事务；Redis 断开不丢任务；恢复后自动补投；Worker 异常可回收；任务最终状态可观测；导入导出走任务队列。

### P4 当前实现状态（2026-09-20）

- 已完成 `tasks` 表、0004 迁移、任务创建/列表 API，以及 `tasks.view` / `tasks.create` 权限。
- 已完成 Tasks 管理页面，支持查看 pending 任务并创建新的持久化任务记录。
- 已接入 arq + Redis 投递字段、`background` 队列和最小 Worker；任务创建后先落库，再投递，Redis 不可用时保留 `pending`。
- 已验证 `worker.smoke.2` 从 `pending` 进入 `succeeded`；重试、进度、取消、恢复和 outbox 补投均已落地。
- 已增加任务进度、消息、尝试次数和取消 API；Worker 会更新 `running` / `succeeded` 与进度，`tasks.cancel` 仅允许取消 pending 任务。
- 已增加 `tasks.retry` 和失败任务重试入口；开发用 `force_fail` Payload 已验证 `pending → running → failed`，页面可将失败任务重新置为 pending 并生成新的 arq Job ID 重新投递。
- 已补齐前端 Task Action Guard：创建、取消、重试按钮分别受 `tasks.create`、`tasks.cancel`、`tasks.retry` 控制；后端权限校验仍是最终边界。
- 已增加 Worker 启动恢复与 30 秒 cron 补投：扫描 `pending + published_at IS NULL` 任务，Redis 恢复后自动投递并回写 Job ID；已通过真实 PostgreSQL、Redis 恢复烟测。
- 已增加 Worker lease 回收：新增 `started_at` / `error_message` 与 0007 迁移；超时 running 任务按 `max_attempts` 回到 pending 或进入 dead，已通过真实数据库烟测。
- 已增加 0008 `task_events` 时间线和 0009 历史任务回填：创建、发布、开始、成功、失败、取消、重试、lease 回收和 dead 状态都会记录事件；Tasks 页面通过受保护的事件 API 展示时间线。
- `/api/v1/health` 已增加不缓存的 `tasks` 聚合统计（total/pending/running/failed/dead），Dashboard 的 queued tasks 卡片读取真实 pending 数量。
- 已修复前端过期 Token 导致 `/login` 与 `/` 无限重定向的白屏问题；认证失败现在会同时清除本地访问令牌。

## P5：Resource Contract 与 Manifest

```text

```

v1 范围：Resource、Field、Table、Form、Filter、Action、Bulk Action、Relation、Query Metadata、Permission Metadata、Manifest Compiler、Vue Renderer Registry。

门禁：Manifest 可校验、可版本化、可生成 TypeScript 类型；不引入 Low-Code、动态 JS 或可视化设计器。

### P5 当前实现状态（2026-09-20）

- 已为 Users/Roles 建立首批资源定义；Manifest 只输出 JSON-safe 元数据，字段标题使用 i18n key，不携带 SQLAlchemy Model、函数或敏感信息。
- 已增加受 `users.view` 保护的资源目录接口：`GET /api/v1/admin/resources` 与 `GET /api/v1/admin/resources/{name}`。
