# 任务队列（Task Engine）设计

**状态：** 方案已定（**B：arq + Redis 作执行器，PostgreSQL 作任务记录与 outbox**），OPEN-08 关闭；实现排入 Phase 4。
**配套：** `docs/项目约束.md`、`docs/阶段开发计划.md` P4（B-09、D-07、X-04、X-14、B-21、R-12、RB-10）
**本文不动代码**：只定接口、数据模型、失效路径；实现按 §13 的验收清单在 Phase 4 落地。

---

## 1. 为什么现在要定这件事

约束早就规定「必须有条队列」，只是没规定是哪一条：

- **B-09**：禁止在 async endpoint 内做长阻塞任务，重任务走任务队列；
- **D-07**：耗时任务不得阻塞请求线程；
- `docs/功能取舍集成.md`：`BackgroundTasks` 只做轻量后处理，Job Queue 属「后续独立 Task Engine」，Infrastructure Adapter 预留 `Queue`；
- OPEN-08：队列/Worker 选型最迟 Phase 4 决定。

Phase 3/4 一定型就会立刻用到它：Resource 的**导入/导出**（OPEN-07）、审计归档、缓存批量失效、Settings 重算。

---

## 2. 范围与非目标

**做**：一次性异步任务、延迟任务、重试与退避、幂等提交、进度回写、失败可重放、Worker 水平扩展、**Redis 不可用时的降级**。

**不做**（与 R-16 同源，防止框架长成编排平台）：

| 非目标 | 说明 |
| --- | --- |
| DAG / 工作流编排 | 不做 Airflow 式依赖图；任务间联动走 Event Bus（R-12） |
| 可视化流程设计器 | 明确排除 |
| 周期性调度（cron 语义） | 第一期只做「延迟/一次性」，`schedules` 另立（见 §14） |
| 分布式事务 / Saga | 事务边界仍由 Service 显式控制（B-09） |
| 跨语言 Worker、秒级实时流 | 不支持 |

## 3. 分层落点（A-01、A-03、B-11）

```text
server/app/core/tasks/            框架能力，不认识任何业务
├── definitions.py    TaskDefinition + 注册表
├── model.py          SQLAlchemy Model（tasks 表：记录 + outbox）
├── repository.py     状态/进度/发布时间回写（纯 ORM 表达，B-03）
├── service.py        enqueue / retry / cancel / progress（事务边界在此，B-09）
├── broker.py         arq 客户端封装（唯一知道 arq 的地方）
├── enums.py          TaskStatus / TaskSource
├── recover.py        outbox 重投 + 僵尸任务回收（Redis 恢复后自愈）
├── errors.py         Domain Error（B-14）
└── __init__.py       生命周期钩子（B-21）

server/app/modules/tasks/         业务模块：把 Core 能力暴露成 API + 后台页面
worker/tasks_worker.py            arq Worker 入口（独立进程，复用同一套 handler 注册）
```

依赖方向：`modules/tasks → core/tasks → infrastructure`；Core 不 import 业务模块（A-01），业务模块只在自己的 `module.py` 里注册 handler（A-06）。
`arq` 只允许出现在 `core/tasks/broker.py` 与 worker 入口两处 —— 换 broker 时其它文件不动（X-02、X-06）。

## 4. 方案与取舍（已定）

**双写但职责不同：**

| 角色 | 载体 | 负责什么 |
| --- | --- | --- |
| 执行通道 | **arq + Redis** | 投递、可见性超时、并发消费、重试退避、多 Worker 水平扩展 |
| 事实记录 | **PostgreSQL `tasks` 表** | 任务状态、参数、进度、结果、错误、触发人、幂等键，兼作 **outbox** |

这样切分的收益：**「业务写 + 任务记录」在同一个事务里**（不丢任务、不重复排队），而 Redis 只承担「什么时候被拿起来跑」。Redis 挂掉时任务**不会消失**，只是没人执行 —— 这正是 §7 降级设计成立的前提。

**为什么不选 PG-only 队列（方案 A）**：`FOR UPDATE SKIP LOCKED` 属 PostgreSQL 独有能力，按 X-09⑤ 一旦批准就等于放弃 X-14 的 MySQL 目标。**本方案完全不使用任何方言专有语法**：只有 `INSERT/UPDATE/SELECT` + 普通索引 + `sa.JSON`，全部落在 PG ∩ MySQL 交集内（X-09、X-10、X-11 保持满足）。

**为什么不选 Celery（方案 C）**：worker 是同步模型，要在里面跑本项目的 async SQLAlchemy 栈必须另起事件循环，与 D-04「全链路 Async」摩擦大，且 beat/result backend/序列化配置的面太大。arq 原生 asyncio，与 FastAPI 同一套栈。

## 4.1 新增依赖清单（X-06、W-05 备案）

| 依赖 | 用途 | 维护成本 |
| --- | --- | --- |
| `arq` | 队列 broker + worker（asyncio 原生） | 单一作者、API 面小；锁版本 |
| `redis` | 已在 Phase 0 引入（缓存用），队列复用同一客户端 | 无新增 |
| 现有 `asyncpg` / SQLAlchemy | 任务记录读写 | 无新增 |

Redis 仍是**可选基础设施**（X-04）：**系统启动、缓存、Web 服务都不依赖它**；只有「任务被实际执行」依赖它，未配置时队列进入 §7 的暂停态并可自愈。

## 5. 数据模型

```text
tasks
  id                 BigInt PK
  name               String(128)   注册名，如 "imports.run"
  queue              String(32)    default / background / heavy
  status             String(16)    pending / running / succeeded / failed / dead / cancelled
  args               JSON          仅可序列化数据；禁止 Secret（RB-06、B-28）
  result             JSON          完成摘要（大对象另存并回链）
  error              Text          最后一次失败原因
  attempts           Integer default 0
  max_attempts       Integer default 3
  idempotency_key    String(190)   UNIQUE（可空）—— 同一 key 返回同一任务
  run_at             DateTime(tz)  计划执行时间（延迟与退避都改这个字段）
  broker_job_id      String(190)   arq job id；未投递成功时为 NULL ← 降级判据
  published_at       DateTime(tz)  成功投递给 broker 的时间（可空）
  started_at / finished_at  DateTime(tz)
  worker_id          String(64)    哪个 worker 在跑
  progress           SmallInt      0..100
  priority           SmallInt      1 最高
  actor_user_id      BigInt FK users.id   谁触发的（RB-09）
  request_id         String(64)    串起「前端报错 → API → 任务 → 日志」（B-29）
  created_at / updated_at

task_events（可选，见 §14）
  id / task_id FK / type / message / created_at   —— 重试、进度、降级与恢复的时间线
```

索引：`(status, published_at)`（recovery 扫未投递）、`(status, run_at)`、`idempotency_key` 唯一、`actor_user_id`。
类型纪律全按 **X-10**：`String` 显式长度、`DateTime(timezone=True)` + 应用层产生 UTC、枚举 `sa.Enum(native_enum=False)`、JSON 用 `sa.JSON` 且不建表达式索引。
迁移两条 revision，成对可逆（X-12），进 `scripts/check_migrations.py` 与往返门禁（Q-03）。

**交集纪律**：不得使用 `ILIKE`、`citext`、JSONB 表达式索引、`SKIP LOCKED`（X-09、X-14）。

## 6. Core 接口（先冻结，再实现）

```python
TaskDefinition(
    name="imports.run",
    handler=run_import,                  # async (ctx: TaskContext) -> Any
    queue="background",
    max_attempts=3,
    backoff=exponential(base=2, cap=300),
    timeout_seconds=900,
    idempotency_required=True,
)

await enqueue(
    "imports.run",
    args={"file_id": 12, "mode": "upsert"},
    idempotency_key=f"import:{file_id}:{checksum}",
    run_at=None,
    priority=5,
    session=session,                     # 复用调用方事务，绝不自己 commit（B-09）
) -> TaskHandle
```

`enqueue` 的**唯一提交点**在 Service：

1. 事务内 `INSERT` 一行 `status=pending, published_at=NULL`（幂等键冲突则返回既有任务，不报错）；
2. 事务提交**之后**才尝试投给 arq，成功则 `UPDATE published_at/broker_job_id`；
3. 投失败（Redis 不可达/超时）只记日志并留在 `pending`，由 §7 的恢复路径补投，**不回滚业务事务**。

```python
@dataclass(frozen=True)
class TaskContext:                       # 注入给 handler
    task: Task
    attempt: int
    session: AsyncSession                # 每任务独立 session/事务（B-09）
    request_id: str
    actor_user_id: int | None
    async def progress(self, percent: int, note: str = "") -> None: ...
```

模块注册（A-06）：`ModuleRegistration(name="imports", tasks=[import_task_definition], permissions=("imports.run", "imports.view"))`

Worker 入口：`python -m worker.tasks_worker --queue background --concurrency 4`；生命周期复用 `core/tasks`（B-21），SIGTERM 后停止领取、等在途任务到安全点。

## 7. 降级设计（Redis 不可用 / 部分不可用）

先定义清楚「Redis 挂了」的四种形态与各自处置：

| 场景 | 现象 | 处置 |
| --- | --- | --- |
| 入队时连不上 | `enqueue` 的 broker 步骤抛 `RedisError` | 任务行已在同一事务落库 ⇒ **不丢**。状态留 `pending`、`published_at IS NULL`；API 返回 201 + `data.delivery = "deferred"`（业务成功不因队列抖动而失败）|
| 运行中断（有 pending 未投出去） | outbox 有未投递行 | `recover.py` 每 30s 扫 `status=pending AND published_at IS NULL AND run_at <= now`，按 FIFO 重投；重试次数与业务 `attempts` 分离（`publish_attempts`，上限后置 `dead`）|
| 已投递但 worker 全灭 | 任务停在 `running`，arq 可见性超时后重新可见 | worker 侧 `timeout_seconds` + `keep_result`；PG 行由 `started_at + lease` 超时判定为「僵尸」，回 `pending` 并记录事件；arq 重投由 broker 的 `max_tries` 负责，**以 PG 行为准做幂等复核**（拿到 job 先看 PG 是否已 `succeeded/cancelled`，是则直接 ack 丢弃）|
| Redis 恢复 | broker 可用 | 恢复循环自然把 outbox 清空；页面与日志显示「队列从暂停恢复」|

**关键不变量**

1. **PG 是唯一事实来源**，arq 只是「加速器」。Redis 里没有任何状态是重建不了的（队列内容可由 outbox 重放）。
2. **至少一次投递 + 幂等执行**：handler 必须可安全重放（业务唯一键 / `idempotency_key`）。arq 可能重复投递，PG 行状态机负责收敛。
3. **不因队列不可用而失败业务请求**（入队走同一事务落库）；反过来，需要「任务一定已开始」的调用方要显式轮询 `TaskHandle.status`。
4. **降级可观测**：`/api/v1/health` 的 `tasks` 段暴露不缓存的 `{total, pending, running, failed, dead}` 聚合；broker 不可用时任务仍保留为 pending，后台时间线和状态页不得静默丢失。
5. 系统未配置 Redis 时仍可正常启动与提供全部 Web 能力（X-04）；此时队列进入「只记录不执行」的暂停态，并每 30s 探测一次，配置好即自动排空。

## 8. 状态机

```text
pending ──publish──▶ pending(arq 队列中) ──worker claim──▶ running
   ▲                                                          │
   │ publish 失败（留在 pending，published_at IS NULL）        ├─ ok ────────────▶ succeeded
   └────────────── backoff（attempts+1, run_at 后移） ◀────────┤ 异常且 attempts<max
                                                              ├─ 异常且 attempts≥max ▶ dead
                                                              └─ 取消（仅 pending）  ▶ cancelled
   running 超时（started_at + lease < now） → 回 pending（记事件）
```

状态迁移全部落在 `core/tasks/repository.py` 的 ORM 语句里（B-03），并且带**条件更新**（`WHERE status = :expected`）来防止并发把已完成的任务改回运行中。

## 9. 与既有能力的接线

| 能力 | 关系 |
| --- | --- |
| Event Bus（R-12） | 发 `TaskEnqueued/Started/Progressed/Succeeded/Failed/Dead`；审计与通知只监听事件 |
| Audit（RB-09） | 记录触发人 `actor_user_id` + `request_id`；args 中的敏感字段沿用日志脱敏名单 |
| Settings（R-08） | `tasks.enabled`、`tasks.concurrency`、`tasks.lease_seconds`、`tasks.max_attempts_default`、`tasks.publish_retry_interval_seconds` |
| Cache / Redis（X-04、B-20） | 复用 `core/redis` 的连接与生命周期，**不另起一套 client**；队列可用性探测也走它 |
| Distributed Lock（RB-10，Phase 4） | 需要全局串行的任务（夜间归档）用 `core/lock` 包一层 |
| Resource 导入/导出（OPEN-07） | 大文件导入/导出必须走 Task Engine；HTTP 只负责落文件 + 入队 + 返回 task id |
| Rate Limit（B-19） | 入队接口单独限流，防止刷爆队列 |
| Navigation（R-10） | 任务列表/详情页由 `modules/tasks` 注册 |

## 10. 权限与安全

- 权限命名沿用 RB-02：`tasks.view` / `tasks.retry` / `tasks.cancel` / `tasks.create`；业务任务权限归各模块（如 `imports.run`）。
- 后端守卫一律 `Depends(require_permission(...))`（B-13、RB-04）；UI 隐藏不算权限。
- `args` 不得含 Secret（RB-06）：入队前过脱敏名单，命中即 `VALIDATION_ERROR`；`error` 字段写库前同样清洗。
- handler 不得跨模块直改别人的表（A-09）；只走对方 Service 或 Event。

## 12. 部署形态

- 开发：compose 服务 `postgres / server / worker / redis(profile redis)`。worker 与 server 共用 `DATABASE_URL`（D-01、D-10）。
- 生产：`reverse proxy / server / worker×N / postgres / redis`。worker 数量按队列积压调，不按 CPU 调。
- 迁移只由 `server` 跑（`alembic upgrade head`），worker 不跑迁移（避免并发 DDL，X-12）。
- Redis 用托管实例时按 X-16 处理连接模式；队列侧不需要 prepared statement，事务池即可。

## 13. Phase 4 验收清单

- [ ] 入队与业务写同事务：业务回滚 ⇒ 任务不存在（B-09）
- [ ] `idempotency_key` 相同 ⇒ 返回同一 task id，不产生第二行
- [ ] **断开 Redis 后**：入队仍成功、任务停在 `pending/published_at IS NULL`、Web 功能与启动完全正常（X-04）
- [ ] **恢复 Redis 后**：recovery 在 N 个周期内自动排空 outbox，无需人工干预
- [ ] handler 抛错 → 退避重试 → 超限进 `dead`；`attempts`/`error`/时间线正确
- [ ] worker 被 kill：`started_at + lease` 超时后任务回 `pending`，不出现永久 `running`
- [ ] 重复投递被 PG 状态复核吸收（已 `succeeded` 的 job 直接 ack 丢弃）
- [ ] `progress()` 回写 + 事件发布；审计能看到触发人（RB-09）
- [ ] 无权限调用重试接口返回 `PERMISSION_DENIED`（Q-10 反例）
- [ ] args 含 `token`/`password` 键时入队被拒且日志脱敏（RB-06、B-28）
- [ ] 两条 revision 且 `upgrade → downgrade → upgrade` 往返通过（Q-03、X-12）
- [ ] `grep` 确认 `core/tasks/**` 无 `SKIP LOCKED`/`ILIKE`/`text(`（X-09、X-14、B-03）
- [ ] 门禁全绿
