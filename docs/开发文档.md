# FastAPI + Vue3 Admin Framework

## 架构设计、开发规范与工程约束

**文档版本：** v1.0
**项目阶段：** Admin Foundation
**技术定位：** 通用、模块化、类型安全、可生成 CRUD 的管理后台框架

---

# 1. 项目定位

本项目不是某个具体业务的后台模板，而是一套可长期复用的：

> **FastAPI + Vue 3 + TypeScript + shadcn-vue 通用管理后台框架**

核心目标：

* FastAPI 异步后端
* Vue 3 + TypeScript 管理后台
* shadcn-vue 作为统一 UI 基础
* SQLAlchemy 2.x ORM
* Alembic 数据库迁移
* Pydantic v2 数据验证
* OpenAPI 作为唯一前后端 API Contract
* Scalar 作为默认 API Documentation UI
* OpenAPI 自动生成 TypeScript API Client
* Resource Engine
* Schema/Form Engine
* DataTable Engine
* 企业级 RBAC
* 动态菜单
* Settings Engine
* Audit Log
* Event System
* CRUD Generator
* AI-assisted Generator
* 模块化业务架构
* Docker Compose 部署

项目应允许未来开发：

* CMS
* Blog
* Forum
* Trading
* AI
* Payment
* Membership
* Notification
* Media
* 其他业务系统

这些业务只能作为独立 Module 接入，不允许污染 Admin Core。

---

# 2. 核心设计原则

整个项目必须遵循：

> Core 提供能力，Module 实现业务。

依赖方向只能：

```text
Business Module
      ↓
Admin Core
      ↓
Infrastructure
```

禁止：

```text
Admin Core
      ↓
Trading / CMS / Payment / AI
```

Core 永远不能知道具体业务。

# 11. ORM 规范

ORM 固定使用：

> SQLAlchemy 2.x

数据库结构采用：

> Model First

例如：

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        primary_key=True
    )

    username: Mapped[str] = mapped_column(
        String(64),
        unique=True,
        index=True
    )

    email: Mapped[str] = mapped_column(
        String(255),
        unique=True,
        index=True
    )
```

# 12. SQL 开发约束

普通业务禁止 Raw SQL。

禁止：

```python
session.execute("SELECT * FROM users")
```

禁止：

```python
f"SELECT * FROM users WHERE id={user_id}"
```

禁止：

* Router 写 SQL
* Service 拼接 SQL
* SQL 字符串拼接
* 前端传递 SQL
* Generator 生成 Raw SQL CRUD

统一使用：

```text
SQLAlchemy ORM
SQLAlchemy Select
SQLAlchemy Relationship
SQLAlchemy Expression Language
```

Raw SQL 仅允许用于：

* ORM 无法合理表达的复杂查询
* 明确验证过的性能优化
* 特殊数据库能力

并必须独立封装。

# 17. Scalar API 文档集成

Scalar 作为默认 API Documentation / Explorer，使用 FastAPI 官方集成方式接入。后端依赖 `scalar-fastapi`，由 `main.py` 在应用创建阶段注册，不在 Vue 中重复实现一套 API 文档页面。

## 17.1 固定路由与职责

```text
/docs/scalar
    Scalar API Reference / Explorer

/openapi.json
    FastAPI 生成的唯一 OpenAPI Schema
```

选择 `/docs/scalar` 是为了避免与 FastAPI 默认 Swagger UI 的 `/docs` 路由冲突。Scalar 只负责：

* API Documentation
* API Explorer
* Request Testing
* Schema Visualization

Scalar 不作为 API Contract Source。真正的 Source 是 FastAPI 根据 Pydantic Schema、Router 和依赖生成的 `/openapi.json`；TypeScript SDK、前端 Query 层和 Scalar 都消费同一份 Schema。

## 17.2 推荐注册方式

```python
from scalar_fastapi import add_scalar_reference

add_scalar_reference(
    app,
    route="/docs/scalar",
    openapi_url=app.openapi_url,
    include_in_schema=False,
)
```

实现时必须封装到 `server/app/core/openapi/` 或等价的 Core 注册器中，`main.py` 只负责调用注册器。依赖、路由和配置不得散落在业务 Module 中。

## 17.3 配置与安全边界

```env
API_DOCS_ENABLED=true       # 开发环境 true；生产环境默认 false
SCALAR_TELEMETRY=false     # 自托管项目默认关闭
SCALAR_AGENT_ENABLED=false # 默认关闭 Scalar Agent
SCALAR_THEME=KEPLER
SCALAR_JS_URL=             # 留空使用集成默认地址；内网部署可改为自托管资源
SCALAR_PROXY_URL=          # 仅在明确需要代理时配置
```

约束如下：

1. `API_DOCS_ENABLED=false` 时不注册 `/docs/scalar`，但 `/openapi.json` 是否开放由生产 API 网关策略决定。
2. 生产环境不得默认暴露可执行的在线 API Explorer；如需开放，必须配合网关 allowlist、管理员鉴权或内网访问控制。
3. OpenAPI 中的 OAuth2/Bearer Security Scheme 必须完整生成，开发者可在 Scalar 中使用登录接口获取的 Token 进行授权测试；Scalar 不绕过后端权限。
4. Scalar Agent、遥测和外部代理不属于核心 API 文档能力，默认关闭；启用时必须经过配置审查，不能把密钥提交到仓库。
5. 不能在 Scalar 配置中写死数据库、JWT Secret、Provider Key 或其他敏感信息。

## 17.4 文档内容规范

每个 Router 必须声明稳定的 `tags`、summary、description、Request/Response Schema、错误响应和鉴权依赖。新增 API 的完成定义为：

```text
Router/Schema
    ↓
OpenAPI 可生成
    ↓
Scalar 可浏览和试调用
    ↓
SDK 可生成
    ↓
API Contract Test 通过
```

Scalar 页面显示异常时，先检查 `/openapi.json`；不得通过手写 Scalar 配置掩盖 FastAPI Schema 错误。

# 25. shadcn-vue 设计约束

UI 基础统一采用：

> shadcn-vue

原则：

> 不重新设计 shadcn-vue。

项目允许使用已批准的 Deep Blue 主题，但只能通过 `admin/src/theme-overrides.css` 的全局 `--app-*` Token 和 shadcn 语义 Token 映射实现。登录页、Admin Shell、Resource Center、权限管理和后续模块必须共享同一套 Token；页面级 CSS 只处理布局，不得自行写一套颜色或按钮视觉。

按钮统一使用 shadcn `Button` variant：`default` 用于主操作，`secondary` 用于次操作，`outline` 用于低强调操作，`ghost` 用于导航/工具操作，`destructive` 用于危险操作。任何新页面在合并前必须验证 light/dark、hover/focus/disabled 和窄屏状态。

禁止无需求情况下：

* 修改基础配色体系
* 修改 Radius System
* 修改 Shadow System
* 自创 Button Style
* 自创 Input Style
* 自创 Dialog Style
* 引入第二套 UI Framework

禁止混用：

```text
Element Plus
Ant Design Vue
Naive UI
Vuetify
Semi Design
```

# 90. 最终开发原则

所有开发人员和 AI Coding Agent 必须遵守以下最高优先级原则：

### 原则一

```text
Module First
```

业务按模块组织。

### 原则二

```text
Contract First
```

OpenAPI 是前后端唯一 Contract。

### 原则三

```text
ORM First
```

普通业务使用 SQLAlchemy，不写 Raw SQL。

### 原则四

```text
Resource First
```

标准 CRUD 优先 Resource Engine。

### 原则五

```text
Reuse First
```

优先复用 Admin Foundation。

### 原则六

```text
Core Stable
```

业务不得污染 Core。

### 原则七

```text
Generated ≠ Custom
```

生成代码和人工业务代码必须建立明确边界。

### 原则八

```text
AI assists architecture.
AI does not redefine architecture.
```

AI 可以实现既定架构，但不得自行改变项目技术路线。

# 92. 项目最终目标

本项目最终应达到：

> 开发者定义一个业务 Module / Resource 后，可以自动获得数据库模型、Migration、Pydantic Schema、Repository、Service、REST API、OpenAPI、Scalar 文档、TypeScript SDK、Vue CRUD 页面、菜单、权限、搜索、过滤、分页、批量操作和测试骨架。

# 93. AI Coding 强制执行摘要

每次开始开发新功能之前，必须按以下顺序执行：

```text
1. Identify Module
        ↓
2. Read Existing Architecture
        ↓
3. Check Existing Core Capability
        ↓
4. Check Existing Admin Component
        ↓
5. Check OpenAPI Contract
        ↓
6. Reuse Existing Infrastructure
        ↓
7. Implement Module
        ↓
8. Generate / Update SDK
        ↓
9. Run Migration
        ↓
10. Run Type Check
        ↓
11. Run Tests
        ↓
12. Verify Build
```

任何 AI Agent 不得为了快速完成单个 Task 而绕过上述架构。

**架构一致性优先于短期代码量减少。**

这份可以直接作为项目根目录的 `DEVELOPMENT.md` / `ARCHITECTURE.md` 基线。下一步比较值得继续细化的是 **Resource Engine、Form Engine、DataTable Engine、CRUD Generator 的可执行接口定义和数据结构**，因为这四部分会真正决定这个后台框架是不是“类似 Filament 的开发体验”。
