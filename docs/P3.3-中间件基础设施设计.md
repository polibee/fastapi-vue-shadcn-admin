# P3.3 Middleware Foundation 设计

**状态：** 已实现基础版本，进入集成验证阶段  
**适用项目：** FastAPI Vue Admin  
**目标：** 在使用 FastAPI/Starlette 原生能力的前提下，建立面向生产环境的统一请求管线，为后续限流、Telemetry、认证和模块化开发体验提供稳定基础。

## 1. 设计目标

本阶段只建设基础设施层，不复制 Goravel 的 HTTP 框架，也不把业务认证、RBAC 或 Data Scope 塞进一个大型 Auth Middleware。

目标包括：

1. 每个请求都有可追踪的 Request ID。
2. 请求上下文可被 Service、Audit、Event 和日志读取。
3. 访问日志包含方法、路径、状态码、耗时和 Request ID。
4. 前后端分离访问具有明确的 CORS 配置。
5. 生产环境校验 Host Header。
6. 统一添加基础安全响应头。
7. 统一记录请求耗时，并为后续 Telemetry 保留扩展点。
8. 所有中间件均可单独测试、配置和关闭。

## 2. 非目标

本阶段不实现：

- 全局 Auth Middleware。
- 全局 RBAC Middleware。
- 业务模块查询或数据库访问。
- Rate Limit Engine 的完整实现；本阶段只预留挂载点。
- OpenTelemetry Exporter。
- Server-side Session。
- gRPC、邮件、文件存储和 AI SDK。

## 3. 当前实现映射

- `server/app/core/middleware/request_id.py`：Request ID 生成、透传和响应回写。
- `server/app/core/middleware/request_context.py` 与 `server/app/core/context.py`：请求上下文。
- `server/app/core/middleware/timing.py`：响应耗时头。
- `server/app/core/middleware/access_log.py` 与 `server/app/core/logging.py`：结构化访问日志和敏感字段脱敏。
- `server/app/core/middleware/cors.py`：CORS 配置边界。
- `server/app/core/middleware/trusted_host.py`：Host Header 校验边界。
- `server/app/core/middleware/security_headers.py`：基础安全响应头。

P3.3 的运行时接入点统一位于 `server/app/main.py`；认证、RBAC、Data Scope 仍由 Dependency、Policy、Service 和 Repository 负责。

认证继续使用 FastAPI Dependency：

```python
Depends(get_current_user)
Depends(require_permission("users.update"))
```

授权、Data Scope 和业务策略继续由 Dependency、Policy、Service 和 Repository 协作完成。

```text
server/app/core/
├── middleware/

│   ├── request_context.py
│   ├── access_log.py

│   └── security_headers.py

```

`middleware/` 只依赖 Core、配置和基础设施，不允许导入 `server.app.modules.*` 的 Service、Repository 或 Model。

## 4. 请求管线

概念请求流：

```text
Request
  ↓
Trusted Host
  ↓
CORS
  ↓
Request ID
  ↓
Request Context
  ↓
Timing / Access Log
  ↓
FastAPI Router
  ↓
Authentication Dependency
  ↓
Permission / Policy Dependency
  ↓
Service / Repository
  ↓
Response
  ↓
Security Headers
```

Starlette 中间件的实际执行顺序必须通过集成测试确认，不能仅依据注册顺序推断。

## 5. 组件职责

### 5.1 Request ID

- 优先读取请求头 `X-Request-ID`。
- 缺失时生成 UUID。
- 写入 `request.state.request_id`。
- 响应始终返回 `X-Request-ID`。
- 长度、字符集和最大长度必须校验，避免日志注入和异常大 Header。

### 5.2 Request Context

上下文第一版包含：

```python
request_id: str
trace_id: str | None
user_id: int | None
ip: str | None
user_agent: str | None
method: str
path: str
started_at: datetime
```

用户身份由认证 Dependency 成功后补充，Middleware 不查询用户表。

上下文访问方式应提供类型化 Helper，禁止在业务代码中散落读取 `request.state` 字符串键。

### 5.3 Access Log

默认输出结构化 JSON，至少包含：

```json
{
  "request_id": "...",
  "method": "GET",
  "path": "/api/v1/users",
  "status_code": 200,
  "duration_ms": 18.4,
  "user_id": 1,
  "client_ip": "127.0.0.1"
}
```

禁止记录：

- Authorization Header。
- JWT、密码、数据库 URL、Redis URL。
- 请求体中的密码和 Token 字段。

健康检查、静态资源和高频探针可以通过配置降低日志级别，但不得丢失错误响应日志。

### 5.4 Timing

- 使用单调时钟计算耗时。
- 记录毫秒级 duration。
- 5xx 和超过慢请求阈值的请求必须记录 Warning。
- 不在 Timing Middleware 中做指标上报；只向 Context/Log 提供数据。

### 5.5 CORS

配置项：

```text
CORS_ENABLED
CORS_ALLOW_ORIGINS
CORS_ALLOW_METHODS
CORS_ALLOW_HEADERS
CORS_ALLOW_CREDENTIALS
```

生产环境禁止使用 `*` 与 Credentials 同时启用。默认只允许配置中的明确来源。

### 5.6 Trusted Host

开发环境允许本地开发主机；生产环境必须配置明确的 Host 白名单。

配置项：

```text
TRUSTED_HOSTS
TRUSTED_HOSTS_ENABLED
```

未配置生产白名单时，应用启动检查应给出明确错误或降级警告，不能静默接受任意 Host。

### 5.7 Security Headers

第一版响应头：

```text
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

CSP、HSTS 必须根据部署方式单独配置，不能在所有开发环境强制写死，避免破坏 Scalar、Vite 和本地预览。

## 6. 配置与环境策略

配置必须进入现有 `Settings`，不能在 Middleware 文件中读取环境变量。

环境策略：

| 能力 | Development | Test | Production |
|---|---|---|---|
| Request ID | 开启 | 开启 | 开启 |
| Request Context | 开启 | 开启 | 开启 |
| Access Log | 可读文本/JSON | 可捕获 | JSON |
| Timing | 开启 | 开启 | 开启 |
| CORS | 本地前端来源 | 测试来源 | 显式白名单 |
| Trusted Host | 本地 Host | 测试 Host | 显式白名单 |
| Security Headers | 基础头 | 基础头 | 基础头 + 部署策略 |
| Body 脱敏 | 开启 | 开启 | 开启 |

## 7. 错误处理边界

Middleware 只负责请求基础信息和通用响应头。

错误映射继续使用 FastAPI Exception Handler：

```text
ValidationError       → validation_error
AuthenticationError   → authentication_required
AuthorizationError    → permission_denied
DatabaseNotConfigured  → database_not_configured
Unhandled Exception   → internal_server_error
```

所有错误响应都必须能够通过 `X-Request-ID` 关联日志和审计。

## 8. 测试门禁

必须增加：

1. 缺失 Request ID 时自动生成。
2. 传入 Request ID 时安全透传。
3. 响应始终包含 Request ID。
4. Access Log 不包含 Authorization、密码和 Secret。
5. Timing 在正常响应和异常响应中都能记录。
6. CORS 对允许来源和非法来源行为正确。
7. Trusted Host 拒绝非法 Host。
8. Security Headers 出现在正常响应和错误响应。
9. `/api/v1/health`、登录、公开文档和受保护 API 的管线行为符合配置。
10. Middleware 不依赖业务 Module，使用导入边界检查或架构测试约束。

## 9. 验收标准

本阶段完成必须同时满足：

- 后端测试全部通过。
- 现有认证、RBAC、Data Scope、Audit、Task API 无回归。
- 前端健康状态和 API 错误仍能正常显示。
- OpenAPI 文档和 TypeScript SDK 无非预期漂移。
- Development、Test、Production 配置行为有测试覆盖。
- 文档补充启动配置、代理和生产安全说明。
